# Spec — Trash System (soft delete + 7-day retention + auto-purge)

**Roadmap source:** PhotoSphere_AI_Master_Roadmap.md § 11 (photo management CRUD) + § 3 (folder management). **SUPERSEDES `specs/photo-deletion.md` on PD1** (hard-vs-soft delete) and **SUPERSEDES `specs/folder-mgmt-download-search.md` Part P4's F1/F2 delete behavior** (folder delete becomes soft-delete-with-trash; F1's live-guest-share guard is UNCHANGED and still runs first).
**Status:** draft — Abhishek's trash decision (below) is a HARD REQUIREMENT, not a recommendation. Six sub-decisions (T1–T6) are genuinely open with recommended defaults; two (T2, T5) most need an explicit nod before Developer builds.
**Written by:** Planner Agent, 2026-07-08

## Problem

Abhishek made an explicit, final product decision that overrides `photo-deletion.md`'s PD1 recommendation (hard delete) and revises the already-shipped, already-pushed P4 folder-delete behavior (`057605c`+`9664b6b`): **deleting a photo or folder must be reversible for 7 days**, not immediate and permanent. Today:

- No photo-delete path exists at all (confirmed gap, scoped in `photo-deletion.md`, not yet built).
- Folder-delete (`DELETE /api/folders/:id`) is BUILT, PUSHED, and hard-deletes the folder row immediately, moving its photos to Unfiled with no recovery — this must change.
- There is no soft-delete pattern anywhere in the schema, no scheduled/repeating job mechanism (BullMQ jobs here are all triggered per-event: upload → pipeline, reclassify → reclassify job; nothing runs on a timer), and every photo/folder-listing query in the codebase assumes every row it returns is "live" — none of them know to exclude a trashed item.

This spec is the single build target for both photo delete AND the folder-delete revision, replacing photo-deletion.md's PD1 and folder-mgmt-download-search.md's F2 outcome (soft-delete instead of hard-delete/move-to-Unfiled), while explicitly preserving F1 (guest-share guard, unchanged) and reusing PD3/PD4/PD5/PD7's already-sound analysis (duplicate-chain handling, `photoCount` reconciliation, bulk-delete shape, honest confirm copy) retargeted from "delete" to "soft-delete/trash."

## Hard requirements (Abhishek's explicit decision — NOT open for re-debate)

1. **Soft delete for both photos AND folders.** "Deleting" moves the item into a Trash state (`deletedAt` set). The DB row and storage objects are NOT removed at delete time.
2. **7-day retention**, then **automatic permanent purge** (hard-delete, no user action required).
3. **User-facing message on delete**: to the effect of "available in Trash for 7 days." (Frontend copy — see T6, not overspecified here.)
4. **A Trash surface** with three actions: **Recover**, **Delete permanently** (this one item now), **Empty trash** (everything now).
5. **Applies to folders too** — revises the shipped P4 folder-delete. F1 (guest-share guard) is UNCHANGED and still runs FIRST; trash only governs what happens to a delete F1 already allowed through.
6. **Guest-shared single photo (PD2-successor):** F1's block-while-shared rule for FOLDERS is unchanged. For a single PHOTO whose folder is shared, Abhishek has not re-decided this explicitly. **Recommended default: allow deletion, no block** — the guest gets an ordinary 404 next time, and trash makes this *strictly safer* than photo-deletion.md's original hard-delete framing, since the owner can recover within 7 days if it was a mistake. Flagged as open for an explicit nod (T2), recommend proceeding on this default so backend build isn't blocked.

## Hard constraints (carried over, unchanged)

- Local-first only; additive migration only, continuing from `20260705154110_add_audit_log`.
- `requireAuth` + `asyncHandler` + Zod on every route; 404-not-403 on ownership mismatch.
- Owner-scoped throughout; opaque session tokens unaffected.
- `serializableTransaction()` for any `photoCount` reconciliation.
- No new rate limiter unless justified (none is, here — owner-on-own-data).

## Goals

- Give the owner a reversible way to remove a photo or a folder (single + bulk for photos), with a 7-day undo window.
- Make trashed items invisible everywhere except the Trash surface itself — no leak into search, browse, guest views, dashboard stats, or any listing.
- Auto-purge anything past 7 days without manual intervention, safely and idempotently.
- Preserve F1 (guest-share guard on folders) exactly as shipped.
- Ship a backend fully buildable and Tester-verifiable over HTTP, independent of the Trash-page UI decision.

## Non-goals (this pass)

- Any change to F1's guard logic itself, or to the merge endpoint (merge still hard-deletes the merged-away source folder immediately — merging is not "deleting," it's consolidating; not in scope for trash unless Abhishek says otherwise — flag if this is wrong).
- Versioned/multiple-restore-points, trash size quotas, or per-item retention overrides.
- Any change to `lib/dedup.ts`'s duplicate-detection algorithm itself.
- Undeleting something already permanently purged (impossible by definition).

## Schema change (additive, new migration)

```prisma
model Photo {
  ...
  deletedAt DateTime? @map("deleted_at")
  ...
  @@index([ownerId, deletedAt])   // trash listing + purge-job query
}

model Folder {
  ...
  deletedAt DateTime? @map("deleted_at")
  ...
  @@index([deletedAt])           // purge-job query across all owners
}
```

**T1 — store `purgeAt` explicitly, or derive `deletedAt + 7 days` at read/job time?**
Recommended default: **derive, don't duplicate.** No `purgeAt` column. `daysRemaining`/`purgeAt` are computed (`deletedAt + 7 days`) wherever needed — the Trash listing endpoint, the purge job's query (`deletedAt < now() - 7 days`). Justification: matches this codebase's existing bias (the audit log's fire-and-forget design, `Folder.photoCount` derived-not-recounted patterns) — a stored `purgeAt` risks drift if the retention window ever changes (every existing row's `purgeAt` would be silently wrong) and adds a column that carries zero information not already in `deletedAt`. Retention length becomes one named constant (`TRASH_RETENTION_DAYS = 7`), changeable in one place. Veto toward storing `purgeAt` if Abhishek wants per-item retention override capability later (not requested).

## What happens to a folder's photos when the FOLDER is trashed

**T-folder-photos (stated as the recommended default, not a numbered open decision — low ambiguity):** photos are **NOT individually marked deleted**. They keep their `folderId` pointing at the (now-hidden) folder and are hidden **transitively** — every listing query that resolves a folder's photos already checks folder ownership/visibility, so once the folder query excludes trashed folders, its photos become unreachable by construction. Restoring the folder restores access to all its photos automatically, zero photo-level bookkeeping.

Justification: avoids double-marking (photo AND folder both getting a `deletedAt`), avoids the awkward edge case of "recover this one photo independently while its folder is still trashed" (which the hard requirement doesn't ask for), and matches the folder's `photoCount` staying untouched (below) — the photos never left the folder, they're just not reachable while the folder is trashed.

**Implication for photo-level listing/search:** `GET /api/search`, `GET /api/folders/:id/photos`, etc. must ALSO exclude photos whose **folder** is trashed, not just photos with their own `deletedAt` set — see the full listing-query audit below. A photo can be hidden two ways: its own `deletedAt`, or its folder's `deletedAt`. Both must be checked everywhere.

## `photoCount` under trash/restore

**Stated as settled, not really open:** a folder's `photoCount` is **untouched** by folder-trash/restore — the photos never left the folder (per the above), so there's nothing to reconcile. This is DIFFERENT from a photo-level soft-delete, which DOES decrement the folder's count (the photo leaves the folder's live view, same semantic as the old hard-delete). No `serializableTransaction()` needed for folder-trash/restore itself; still needed for `DELETE /api/photos/:id` decrementing its folder's count, and for `POST /api/photos/:id/restore` re-incrementing it (guarded increment, mirroring the existing guarded-decrement pattern).

## FINAL DECISIONS (2026-07-08, Abhishek — supersede every "recommended default" below where they conflict)

1. **T5 = Option A, DECIDED:** folder purge cascades to hard-delete its photos too. **Option B (spill photos to Unfiled on folder purge instead) is explicitly LOGGED as a real future feature request — NOT built this pass.** Add a line to `agents/STATUS.md`'s backlog noting it.
2. **T2 = REVERSED from the original recommendation:** a single photo CANNOT be deleted if its folder has a live guest `folder_permission` — same posture as F1, no special-casing for single photos. `DELETE /api/photos/:id` and each item in `POST /api/photos/bulk-delete` must run the SAME `hasLivePermission(photo.folderId)` guard F1 already uses (reuse the helper from `routes/folders.ts`, promote to a shared lib if convenient) and return 409 if the photo's folder is live-shared. This replaces AC bullet "T2 recommended default" below.
3. **T7 = FIXED, not deferred.** Use a **Postgres partial unique index** (`CREATE UNIQUE INDEX folder_active_name_unique ON folders (collection_id, name) WHERE deleted_at IS NULL;`) via a hand-edited raw-SQL migration, and **remove** the plain `@@unique([collectionId, name])` from the Prisma schema (replace with a non-unique `@@index([collectionId, name])` for query performance — Prisma's schema DSL can't express a partial unique index, so the constraint lives ONLY in the raw migration SQL; document this loudly in the migration file's header comment and in `schema.prisma` next to the `@@index` so a future schema-drift check doesn't "fix" it back to a plain `@@unique`). Effect: a trashed folder no longer occupies its name slot — a new live folder (manual or worker-auto-created) with the same name can be created immediately, no 409, no interim friction. The trashed row's `name` column is untouched (never mangled/renamed) — the Trash listing always shows the real name.
4. **Folder-restore collision, DECIDED:** if restoring a folder collides with a LIVE folder of the same name (now only possible if a NEW same-named folder was deliberately created after the old one was trashed — decision 3 makes this easy to do), do NOT just 409-and-stop. `POST /api/folders/:id/restore` takes an optional body `{ onConflict?: "merge" | "rename", newName?: string }`:
   - No body / no conflict → normal restore (clears `deletedAt`).
   - Conflict AND no `onConflict` provided → **409** `{ error: "conflict", conflictingFolderId, conflictingFolderName }` (lets the frontend show the choice).
   - `onConflict: "merge"` → clears the restored folder's `deletedAt` is NOT what happens; instead, run the EXISTING merge machinery (`POST /api/folders/:id/merge`'s internals) treating the restored folder as source and the live same-named folder as target: move all the restored folder's photos into the live one (reconciling `photoCount` via `serializableTransaction()`), then hard-delete the now-empty restored folder row (it was already logically "gone" per the user's request — no need to leave a second trashed copy around). Return the merge-style response shape.
   - `onConflict: "rename"` + `newName` (Zod: same trim/min1/max255 as the existing rename schema) → restore the folder (clear `deletedAt`) AND rename it to `newName` in the same transaction; if `newName` ALSO collides (rare), 409 again with the same shape (let the user pick another name — no infinite-retry loop needed server-side).
5. **Photo-restore when its folder is ALSO currently trashed, DECIDED:** `POST /api/photos/:id/restore` first checks whether `photo.folder.deletedAt != null`. If so, **automatically restore the folder first** (recursively applying decision 4's collision handling — if the folder's restore hits a name collision, the PHOTO restore call itself returns that SAME 409 conflict shape from decision 4, unresolved, and does NOT restore the photo yet; the frontend resolves the folder's conflict first via the folder-restore endpoint, then retries the photo restore, which will now find the folder live and proceed normally). If the folder restores cleanly (no collision), proceed to also clear the photo's own `deletedAt` and re-increment the folder's `photoCount`, in the same request. **Note (impossibility, not a gap):** the case Abhishek originally described — "the folder is fully gone, recreate it from scratch" — cannot occur while decision 1 (Option A) is in effect: a fully-purged folder has already taken its photos down with it, so there is no surviving photo to restore into a recreated folder. This scenario becomes relevant again if/when Option B is built later; no design is needed for it now.

## Restore name-collision (folders) — superseded by FINAL DECISION 4 above, kept for context

**T3 original recommendation (409-and-stop, no resolution offered) is REPLACED by decision 4's merge/rename choice.** The mechanism (`P2002` off the unique constraint) is now largely moot given decision 3 (partial unique index means a plain restore rarely collides at all — only when the user deliberately created a new same-named folder after trashing the old one) but the collision-handling code path (decision 4) still must exist for that deliberate-recreation case.

## The auto-purge job

**T4 — mechanism, scoped concretely.** BullMQ's **repeatable job** feature (`Queue.upsertJobScheduler`, available in the installed `bullmq` version — confirm at build time; if the installed version predates `upsertJobScheduler`, fall back to the older `queue.add(name, data, { repeat: { pattern: cron } })` API, functionally equivalent for this use case) is the idiomatic mechanism — this is new infrastructure (existing jobs are all per-event: `pipeline`, `reclassify`), but it's a natural extension of the SAME queue/worker process already running (`lib/queue.ts` / `worker.ts`), not a new service.

- **New job name** `"trash-purge"` on the existing `PHOTO_PROCESSING_QUEUE_NAME` queue (recommended — reuse the queue rather than stand up a second one; the worker already `switch`es on `job.name`), OR a dedicated queue if Developer judges the existing queue's `PhotoProcessingJobData` typing awkward to extend (non-load-bearing, Developer's call).
- **Schedule: once daily** (recommended — 7-day retention doesn't need finer granularity; a daily sweep means worst-case an item survives ~1 day past its exact 7-day mark, acceptable). Registered once at worker startup via `upsertJobScheduler` (idempotent registration — safe to call on every worker boot, it upserts rather than duplicating).
- **Query:** `WHERE deletedAt < now() - 7 days`, separately for `Photo` and `Folder`.
- **Photo purge:** reuses the EXACT hard-delete logic from `photo-deletion.md`'s PD1 design (now repurposed as the terminal step, not the delete-endpoint's immediate action): PD3a's cascade-null of any duplicate pointing at it, PD4's folder-count decrement (**only if not already decremented** — see idempotency below), delete the DB row, then best-effort `deleteObject` the MinIO original + thumbnails.
- **Folder purge — T5 (the one most needing an explicit nod): hard-deleting a trashed folder past 7 days MUST cascade to hard-delete its photos too.** A folder can't be permanently gone while its `folderId`-pointing photos remain in limbo (they'd become permanently-orphaned rows pointing at a nonexistent folder — worse than Unfiled, since nothing surfaces them). Recommended: when a trashed folder's retention expires, the job hard-deletes ALL of its photos first (same per-photo hard-delete logic — DB row + MinIO cleanup — regardless of whether those individual photos ever got their OWN `deletedAt` set, since they were never individually soft-deleted per the "hidden transitively" design above), then hard-deletes the folder row. **This is a deliberate escalation:** a photo the owner never explicitly "deleted" (it was just sitting in a folder the owner trashed) still gets permanently purged once the folder's 7 days run out — this is the necessary consequence of the "photos stay attached, hidden transitively" design (T-folder-photos) and must be stated explicitly so Abhishek can veto it (alternative: on folder purge, move its photos to Unfiled instead of purging them — "the folder is gone but I didn't ask to lose the photos." Flagged as the T5 veto option below).
  - **T5 veto option:** instead of cascading to hard-delete, orphan the folder's photos to Unfiled (`folderId = null`, `deletedAt` stays null on them) at the moment of folder PURGE (not at folder trash-time) — closer to the OLD F2 behavior, but delayed until the 7-day window closes. This preserves photos the owner may not have meant to lose just because they trashed the enclosing folder. Recommended default remains cascade-hard-delete (matches "delete folder" meaning "delete its contents" once truly permanent, and avoids a confusing scenario where recovering a folder's photos via Unfiled after the folder itself is gone feels inconsistent with "the folder was deleted") — but this is explicitly the decision most worth Abhishek's 30 seconds before Developer builds it, since it's irreversible either way once chosen and executed.
- **Idempotency (hard requirement, not a decision):** the job must be safe to run concurrently or be retried without double-deleting or erroring on an already-gone row. Concretely: wrap each item's purge in a check-then-act that tolerates `P2025` (record not found — treat as already-purged, no-op success), and treat `deleteObject` on an already-gone MinIO object as a no-op success (same convention as `photo-deletion.md`'s PD1). Process items one at a time (not a single `deleteMany`) so partial progress on a crash/retry doesn't need to be all-or-nothing — a `deleteMany` WHERE clause is naturally idempotent too (re-running it just deletes zero rows the second time), but the per-item approach is needed anyway to run the MinIO cleanup per photo, so use per-item processing throughout, no separate idempotency mechanism needed beyond "tolerate not-found."
- **Folder-count reconciliation during photo purge:** a photo purged as part of a folder-cascade does NOT touch `photoCount` (the folder is also being deleted in the same job pass — no observer will ever see that folder's count again). A photo purged on its OWN 7-day expiry (not via a folder cascade) has ALREADY had its `photoCount` decremented at soft-delete time (`DELETE /api/photos/:id` decrements immediately, per PD4 retargeted) — the purge job must NOT decrement again (would double-decrement). This is naturally correct if the purge job's photo-hard-delete step simply never touches `photoCount` at all — only the soft-delete endpoints touch it.

## Endpoints (concretely enumerated)

- **`DELETE /api/photos/:id`** — now sets `deletedAt = now()` (was: hard delete under photo-deletion.md's original PD1; that recommendation is superseded). Decrements the folder's `photoCount` (PD4, unchanged reasoning — the photo leaves the folder's live view). Runs PD3a's cascade-null (a duplicate B pointing at this photo A: null `B.duplicateOfPhotoId`) at delete time, not purge time (unchanged from photo-deletion.md — this is a data-hygiene concern independent of hard-vs-soft). 404 not-owned/not-found/**already-trashed** (a second delete on an already-trashed photo is indistinguishable from not-found — 404, not 409, matching "acts like it doesn't exist" once trashed). Audited (`photo_deleted`, retargeted metadata to note `deletedAt`/soft nature). Returns `200 { deleted: true, photoId, folderId, deletedAt, purgeAt }`.
- **`POST /api/photos/bulk-delete`** — unchanged shape from photo-deletion.md's PD5 (partial-success, `{ deleted: string[], failed: [{id, reason}] }`, 100-item cap, no new rate limiter), retargeted to soft-delete. An already-trashed id in the batch → `reason: "not_found"` (same 404-equivalent treatment as single-delete).
- **`DELETE /api/folders/:id`** (existing endpoint, REVISED — breaking change to shipped `057605c`/`9664b6b`) — F1 guard UNCHANGED, runs first. On success, now sets `deletedAt = now()` on the FOLDER instead of hard-deleting the row + moving photos to Unfiled. Photos are NOT touched (per T-folder-photos). `photoCount` untouched. 404 if already-trashed. Audited (`folder_deleted`, metadata now notes soft/trash). Returns `200 { deleted: true, deletedAt, purgeAt }` (drop the old `photosOrphaned` field — nothing is orphaned anymore; note this as a response-shape break for any frontend code already wired to P4's UI, which reads `photosOrphaned` for its confirm-copy — Developer must update that copy too, see T6).
- **`GET /api/trash`** — owner-scoped. **T-trash-shape (recommended, non-load-bearing): two sections in one response** — `{ photos: TrashPhotoCard[], folders: TrashFolderCard[] }`, each item carrying `deletedAt` and computed `purgeAt`/`daysRemaining` (`Math.ceil((purgeAt - now) / 1day)`, floor at 0). Simpler than two separate endpoints/params for a page that needs to render both anyway; a `?type=photo|folder` query param could narrow it later if needed but isn't required now. Paginated per-section (reuse the existing `limit`/`offset` convention, `limit>100` → 400). Trashed-folder photos are NOT separately listed here (T-folder-photos — a trashed folder's card can show its `photoCount` as informational context, but doesn't need to enumerate photos).
- **`POST /api/photos/:id/restore`** and **`POST /api/folders/:id/restore`** — **T-route-naming (recommended, non-load-bearing): keep them on the existing per-resource routers** (`routes/photos.ts`, `routes/folders.ts`) rather than a unified `/api/trash/:type/:id/restore` — this matches the codebase's existing convention of resource-scoped routers (`PATCH /api/photos/:id`, `PATCH /api/folders/:id` live where you'd expect); a unified trash router would be the odd one out. 404 if not owned or not currently trashed (`deletedAt` is null). Photo restore: guarded increment of the folder's `photoCount` (mirrors the guarded decrement pattern, `serializableTransaction()` not strictly required for a single increment but use it anyway for consistency with every other counter touch in this codebase — cheap insurance). Folder restore: 409 on name-collision (T3). Returns the restored item.
- **`DELETE /api/trash/:type/:id`** — **T-permanent-route (recommended): a NEW dedicated trash router** (`routes/trash.ts`, mounted `/api/trash`) rather than reusing the existing single-delete endpoints with a "permanent" flag — overloading `DELETE /api/photos/:id` to sometimes mean soft-delete and sometimes mean hard-delete based on a query param is a foot-gun (a stray `?permanent=true` on a normal delete call would be catastrophic and hard to guard against convincingly); a separate route with a separate, obvious purpose is safer. `:type` is `photo|folder` (Zod enum, unknown → 400). 404 if not owned or not currently trashed. Reuses the exact hard-delete logic from the purge job (photo: cascade-null duplicates + DB delete + MinIO cleanup, no `photoCount` touch since it's already decremented; folder: cascades to hard-delete its photos too, per T5's default). Audited (`photo_permanently_deleted`/`folder_permanently_deleted`, new additive action strings — see audit decision below).
- **`DELETE /api/trash`** (empty trash) — permanently purges EVERYTHING in the owner's trash right now (all trashed photos not under a trashed folder + all trashed folders, each cascading per T5). Owner-scoped only (never touches another owner's trash — trivially true since every query is `ownerId`-scoped). One audit row per item purged, OR one summary row — recommended: **one summary row** (`trash_emptied`, metadata `{ photosDeleted, foldersDeleted }`) rather than N rows, since this is explicitly a bulk user-initiated action distinct from the per-item audit granularity used elsewhere (the per-item precedent — `folder_merged`/`folder_deleted` being one-row-each — was for operations that ARE conceptually one-per-resource; "empty trash" is conceptually ONE action with a bulk effect, closer to how a bulk-delete's *audit* granularity would be argued either way — flag as non-load-bearing, Developer's call to do per-item instead if preferred, doesn't change correctness).

| 15 | `GET /api/guest/folders` | `backend/src/routes/guest.ts` | `getPermittedFolderIds` ∩ live `folderPermission` | The folder include (`include: { folder: {...} }`) must exclude trashed folders — a guest must NEVER see a trashed folder in their list, even if their `folder_permission` row is still technically live (the OWNER trashed the folder; the guest's grant wasn't explicitly revoked, but the folder is gone from their view). Recommend: filter `folder: { deletedAt: null }` inside the include's `where`, or post-filter the permissions array. |
| 16 | `GET /api/guest/folders/:id/photos` | `backend/src/routes/guest.ts` | `getPermittedFolderIds` membership | 404 if the folder is trashed (even though it's in the guest's permitted SET — being in the set means "was granted access," not "still visible"; add an explicit trashed-check after the permitted-set check). Also filter the photo query to `deletedAt: null`. |
| 17 | `GET /api/guest/photos/:id` | `backend/src/routes/guest.ts` | photo lookup + `permittedIds.has(folderId)` | 404 if the photo itself is trashed, OR its folder is trashed (folder-transitive), in addition to the existing permitted-set check. |
| 18 | `GET /api/guest/photos/:id/download` | `backend/src/routes/guest.ts` | same as #17 + permission-level | Same trashed-checks as #17, before the level check (a trashed photo shouldn't even reach the 403-vs-200 permission branch — it's 404 first). |
| 19 | `GET /api/guest/folders/:id/download-all` | `backend/src/routes/guest.ts` | permitted-set membership + `download_all` level | 404 if the folder is trashed, before the level check. The `preflightFolderDownload`/`queryDownloadablePhotos` call underneath (see #20) already needs the fix, which covers this transitively for the photo-set, but the folder-level 404 must be explicit and early (matching #16's reasoning — an OWNER-initiated folder-permission-revoke and an OWNER-initiated folder-trash should both make a shared folder disappear from the guest, one via explicit revoke, one via this trashed-check). |
| 20 | `GET /api/folders/:id/download-all` (owner) | `backend/src/routes/folders.ts` + `lib/folderDownload.ts`'s `queryDownloadablePhotos`/`preflightFolderDownload` | ownership | 404 if the folder itself is trashed (matches #4/#7's "trashed folder = 404 to normal views" pattern). `queryDownloadablePhotos`'s `prisma.photo.findMany` WHERE must add `deletedAt: null` — a soft-deleted photo still has `aiClassificationStatus: "done"` and a real `s3Key` (nothing about soft-delete touches those fields), so WITHOUT this fix a trashed-but-not-yet-purged photo would be zippable, a real data leak through an existing, already-shipped, already-Tester-verified endpoint. **Flag this specifically — it's the clearest "existing code silently becomes wrong the moment trash exists" case in the whole audit.** |
| 21 | `GET /api/dashboard` (stats rollup) | `backend/src/routes/dashboard.ts` | `prisma.photo.count({ where: { ownerId } })`, `prisma.folder.count({ where: { collection: { ownerId } } })`, per-collection `photo.count` | All three counts must exclude trashed items (`deletedAt: null` added to each), or the dashboard's totals will overcount relative to what's actually browsable — a stat inflation bug, not a security leak, but a real correctness regression the moment trash exists. Recommend also considering whether the Trash page should show its OWN count (e.g. "12 items in trash, 7 days left") somewhere on the dashboard — not required by the hard requirements, flag as an optional nice-to-have, not a blocker. |

**Summary: 21 distinct query paths audited; 19 require a code change (all except #10 collections-list and, arguably, none are truly a no-op — even #10's row is included only to show it was considered and correctly excluded).** This table is the Developer's checklist — every row should become a test assertion (a trashed item is invisible at that specific path) in the eventual Tester pass.

**T7 (newly discovered during this audit, not in the original ask) — trashed folder occupies the unique-name slot.** If folder "Nature" is trashed and the user (or the AI worker) tries to create/find-or-create a NEW "Nature" folder before the original's 7 days expire, the `@@unique([collectionId, name])` constraint collides against the TRASHED row, producing an unexpected 409 on an operation that should probably succeed (the trashed folder is, from the user's perspective, gone). **Recommended default: leave as-is this pass (409 on collision, same as today) and treat "rename the old one before restoring, or wait for it to purge" as the acceptable interim UX** — the alternative (excluding trashed rows from the unique constraint, e.g. a partial unique index `WHERE deleted_at IS NULL`) is a real, clean Postgres feature (`@@unique` with a `WHERE` clause needs a raw-SQL migration addition since Prisma doesn't yet support partial unique indexes declaratively) but is more migration complexity than this pass's scope justifies given the low collision frequency (worker auto-recreation is the main realistic trigger, and F5's existing precedent already accepts "the worker may re-create a folder by category name" as benign). Flag for Abhishek: veto toward the partial-unique-index fix if this 409 turns out to be a real annoyance in practice (defer to a follow-up if so — not blocking this spec).
