3. **`POST /api/folders/:id/restore` collision + both resolutions** — PASS, full real collision triggered and resolved both ways:

## Priority 3 — multi-select interaction code review (`frontend/src/app/organize/page.tsx`)

Read `handleCardSelectClick`, `handleSelectAllOnPage`, `handleSelectAllAcrossPages`, and the three `handleGridMouse*` marquee handlers in full (lines ~760–887). Findings:

- **Shift+click contiguous range — correct.** `ids = photos.map(p => p.id)` reads the CURRENT rendered grid order (not some cached/stale order); `fromIdx`/`toIdx` are looked up freshly on every call; the low/high swap (`fromIdx < toIdx ? [fromIdx, toIdx] : [toIdx, fromIdx]`) correctly handles shift-clicking either backward or forward from the anchor. The range is **unioned into** the existing selection (`new Set([...prev, ...range])`), not a replace — this matches Finder/Explorer convention where a second Shift+click extends rather than resets. The anchor (`lastClickedId`) is deliberately NOT moved by a Shift+click (explicit early `return` before `setLastClickedId` would run) — correct, matches the documented intent and standard OS convention (repeated Shift+clicks all measure from the same original anchor, not the last Shift-click target).
- **Ctrl/Cmd+click toggle — correct and isolated.** Creates a fresh `Set` copy of `prev`, adds/removes only `photoId`, touches nothing else in the selection. Does move `lastClickedId` to the toggled card (correct — a plain click or Ctrl-click both become the new anchor for a future Shift+click, matching real desktop file managers).
- **Plain click — correct, with one intentional and reasonable simplification.** `prev.size === 1 && prev.has(photoId) ? new Set() : new Set([photoId])` — clicking the only currently-selected card deselects it (toggle-off), clicking anything else (including when multiple cards are already selected) replaces the whole selection with just that one card. This is standard single-select-click behavior; no bug.
- **Marquee hit-test — correct, uses real DOM rects, not an approximation.** `gridRef.current.querySelectorAll('[data-select-card-id]')` iterates the ACTUAL rendered cards and calls `getBoundingClientRect()` on each one at drag-end time (not a cached/precomputed layout), then does a standard AABB-overlap test (`r.left < rectRight && r.right > rectLeft && r.top < rectBottom && r.bottom > rectTop`) — this is the textbook correct rectangle-intersection formula, not an off-by-one or center-point approximation. Coordinates are consistently `clientX`/`clientY` (viewport-relative) on both the drag-tracking side and the `getBoundingClientRect()` side, and the rendered marquee overlay uses `position: fixed` with the same viewport-relative offsets — internally consistent; no scroll-position mismatch bug.
- **Marquee replace-vs-extend based on modifier at drag START — correct.** `marqueeAdditiveRef.current = e.shiftKey || e.metaKey || e.ctrlKey` is captured in `handleGridMouseDown`, i.e. at the moment the drag begins, and referenced (not re-read) in `handleGridMouseUp` — so releasing/pressing a modifier mid-drag has no effect, only whether it was held at drag-start, exactly as documented and exactly matching the Finder/Explorer convention the code comments claim to follow.
- **Negligible-drag-as-click handling — correct.** A drag under a 3px threshold in both axes is treated as "clicked empty space" and clears the selection (unless the modifier-at-start flag is set, in which case it correctly leaves the selection untouched instead of wrongly clearing it) — a sensible, deliberate choice to avoid a jittery mouse-down/up on empty space nuking an existing selection.
- **"Select all on page" — correctly scoped.** `setSelectedIds(new Set(photos.map(p => p.id)))` only ever reads the current `photos` state array (the current page's data), never anything else.
- **"Select all N across all pages" — genuinely fetches every page, does not fabricate.** `handleSelectAllAcrossPages` loops with `fetchOffset += CHUNK` (100 at a time) calling the real `folderPhotosApi.list`/`unfiledPhotosApi.list` endpoints until `fetchOffset >= res.total || res.photos.length === 0`, accumulating real ids from each response into `allIds` before setting the selection — this is a real multi-page fetch loop, not a UI claim backed by only the current page. On an error mid-loop it deliberately leaves the selection as whatever was already accumulated/selected rather than silently claiming a bigger selection than what was actually fetched — matches the "scoped honestly" comment in the code and the STATUS.md claim.

No suspicious or incorrect logic found in this code on inspection. This is a code-correctness review only, not a substitute for an actual pointer-drag observed in a real browser — that remains unverified (Priority 2 gap).
