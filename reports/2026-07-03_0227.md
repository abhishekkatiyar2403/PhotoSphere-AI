## Methodology / process notes

- **Signup rate-limit budget discipline was tighter than expected this run, and I made one real mistake.** The live dev server enforces `signupRateLimiter` at 5/15min/IP (not relaxed — that only applies under `NODE_ENV=test`, which the live `:4000` process isn't running). My first Playwright spec draft used one signup per test (5 tests in one file) and immediately exhausted the bucket with 4 failures before I caught it. I rewrote the suite to use exactly one signup per file, shared across a `describe.serial` block via a single persistent browser context (not Playwright's default per-test fixture, which creates a fresh, unauthenticated context every test). Separately, while setting up the cross-user isolation check for the dashboard endpoint, I burned two more signup slots on throwaway "is the bucket reset yet" probes before realizing I could just check the `RateLimit-Remaining` response header instead of trial-and-error POSTs — cost about 10 minutes of real wall-clock time waiting out the window, and meant I reused a pre-existing test account (looked up via a **read-only** `prisma.user.findMany` query, no credentials typed anywhere, password recovered only because it's the same hardcoded test constant `correct-password-123` my own spec file used) rather than creating a fresh "User B" for the isolation check. Functionally equivalent test coverage, but worth flagging as a self-inflicted inefficiency for whoever tests this endpoint next: **check `RateLimit-Remaining`/`RateLimit-Reset` response headers before burning a signup as a "is it reset yet" probe.**
- **Progress-bar sampling required two implementation iterations.** My first approach polled `[data-testid="upload-progress"]`'s `value` attribute from Node via repeated `locator.getAttribute()` calls in a `while` loop running concurrently with the upload. This caused a genuine test-harness hang (60s timeout) even though the underlying upload had actually completed successfully (confirmed via the page snapshot in the trace — status: done, labels populated, thumbnail rendered) — the repeated cross-process `getAttribute()` calls appear to have contended with Playwright's single action queue on the same page, starving the `click()`/`expect()` calls queued after them. Fixed by moving all sampling in-page via `requestAnimationFrame` + a plain JS array, read back with one `page.evaluate()` call at the end — zero cross-process contention, and this is what surfaced the 3,521-sample, 181-distinct-value result in test 13. Flagging this as a reusable pattern for any future Tester needing to observe fast-moving DOM state during an in-flight Playwright action.
- **Why CDP throttling, not just a bigger file.** The spec anticipated "a small file this may complete near-instantly... use a larger fixture file... or note if too fast to observe, explaining how you verified the wiring is real rather than cosmetic." A 15MB file completed in under 1 second on localhost/MinIO with no observable intermediate values (test 12) — going bigger wasn't a good option since the next size step (~60MB) exceeds the existing 50MB upload limit and would just 413 before ever reaching the progress-bar code path. Throttling the same request to 2 Mbps via `context.newCDPSession(page).send("Network.emulateNetworkConditions", ...)` exercises the identical client-side code (`xhr.upload.onprogress`) at a speed where progress is genuinely observable, which is strictly stronger evidence than a code review alone (test 13) — I did read the transport code too (`frontend/src/lib/api.ts`'s `uploadFileWithProgress`) and can confirm `xhr.upload.onprogress` correctly computes `event.loaded / event.total` when `event.lengthComputable`, with `onProgress?.(1)` forced in `onload` as a completion floor — but the live throttled run is the stronger claim, not a fallback to it.
- **Dedup note on the dashboard aggregation test:** the byte-identical re-upload of `fixture-food.jpg` (test 4) correctly resolved to `duplicate` via the SHA-256 exact-dedup pass (consistent with the AI-classification cycle's fix) and correctly received no folder assignment, which is why `totals.folderCount` (3) and `collections[0].folderCount`/`photoCount` (3/3) are lower than `totals.photoCount` (5) — this is the exact "duplicates/failures still count toward the library-size stat but don't get organized" behavior the spec's Open Question #1 default describes, and it held up under a live, independently-computed check rather than just trusting the endpoint.
- **MinIO console login skipped on principle**, consistent with every prior report — storage proof here was direct byte-size arithmetic against `storageUsedBytes`, not a console visit.
- **Test residue left behind:** accounts `budget-probe@example.com` (5 photos: food/nature/vehicles/FORCE_FAIL-animals/duplicate-food, plus a 6th `fixture-documents.jpg` from the regression spot-check), `upload-polish-1783024978086@example.com` (3 photos: food, people, the 15MB large-progress-test image — this is "User B" reused from the Playwright run for the cross-user isolation check), plus two other `upload-polish-*` accounts from earlier failed Playwright attempts (no uploads, browser-context/session issues only, no photo data). Several throwaway signup attempts with invalid payloads also hit the DB's rate-limit table but created no user rows. Signup bucket for this IP was fully exhausted at multiple points during the run and self-resets on its own 15-minute schedule — no manual intervention needed, just planning around it next time.
