  - Upload handler stores `fileSha256` at row creation.
  - All new endpoints: `requireAuth` + `asyncHandler` + Zod + 404-not-403 ownership.

## Review-fix pass (2026-07-02, adversarially-verified code review — 9 findings, all fixed)

1. **[MAJOR] SHA-256 exact dedup could produce mutual/circular duplicates** (`worker.ts`). `fileSha256` is written at photo-row creation (before the job runs), so a sibling upload of the same bytes was visible to the exact pass while still unprocessed — two quick uploads of one file marked each other duplicate (A→B *and* B→A) and neither ever classified or foldered. **Fix (option b): symmetry breaker** — the exact pass now matches only strictly-OLDER rows (`createdAt`, `id` tiebreak for identical timestamps) that are not themselves duplicates (`duplicateOfPhotoId: null`), ordered oldest-first so the verdict points at the canonical original. Duplicate edges now always point strictly backwards in time → cycles are structurally impossible. **Trade-off accepted:** in a rapid double-upload the newer sibling is flagged duplicate-of the older even if the older hasn't finished its own pipeline yet; the older always proceeds to classify, and if it ends up `failed` the duplicate-flagged sibling's escape hatch is the reclassify endpoint (vs. option (a), processed-only matching, which would have let both copies of a rapid double-upload classify with no dedup at all — judged the worse trade for the "overwhelmingly common re-upload case" this pass exists for). Covered by the flat-image test's `duplicateOfPhotoId === <older photo id>` assertion. **See the "Finding #1 follow-up" section below — re-verification found this fix incomplete (the pHash phase had the same hole) and it has now been closed properly.**
2. **[MAJOR] Reclassify check-then-act race** (`routes/photos.ts`). The 409 guard, job-row create, status update, and enqueue were four non-atomic awaits — N concurrent requests could all pass the guard and double-enqueue. **Fix: atomic claim** — a single conditional `updateMany({ where: { id, ownerId, aiClassificationStatus: { notIn: ["pending","processing"] } }, data: { aiClassificationStatus: "pending" } })` is now the arbiter; only `count === 1` proceeds to create the job row and enqueue, everyone else 409s. New smoke test fires 6 parallel reclassifies and asserts every response is 202/409 **and** new job rows === number of 202s.
3. **photoCount drift from stale `previousFolderId` reads** (`worker.ts` assignPhotoToFolder + PATCH move). Plain reads under Read Committed could be stale by write time (worker concurrency 2 + concurrent manual moves). **Fix:** both transactions now run at **Serializable isolation with automatic retry on P2034** (new `src/lib/serializableTransaction.ts`, 5 retries, jittered exponential backoff) — Postgres aborts one side of any conflicting pair instead of silently drifting, and the helper retries it. Chosen over recount-per-folder because recounting at Read Committed has the same lost-update window unless the folder rows are locked first; Serializable is the smaller, provably-correct diff.
4. **Reclassify stuck-pending on enqueue failure** (`routes/photos.ts`). Job row + `pending` status were committed before `queue.add` with no compensation — a Redis failure left the photo `pending` forever (every future reclassify 409s). **Fix:** try/catch around job-row create + enqueue; on failure the orphan job row is deleted and the claim released (revert to the pre-claim terminal status, guarded `where aiClassificationStatus: "pending"`), then rethrown so asyncHandler 500s with consistent state.
5. **Reclassify TOCTOU (security lens)** — same root cause as #2; the atomic claim resolves it, and the parallel-burst test's `job rows === 202 count` assertion proves job-row creation is capped at one per claim.
6. **DEGENERATE_PHASH guard had zero automated coverage.** New smoke test generates two DIFFERENT solid-color flat JPEGs (unit-asserts both hash to `DEGENERATE_PHASH`), uploads both — both must reach `done`, neither `duplicate` (the exact Tester flat-image repro) — then re-uploads one byte-identically and asserts `duplicate` with `dedupMethod: "sha256"` pointing at the older original.
7. **Multi-category priority AC untested / fixtures unused.** New smoke test uploads `fixture-people.jpg` (labels span People+Nature → must land in **People** per `CATEGORY_PRIORITY`) and `fixture-nature.jpg` (→ Nature); `fixture-documents.jpg` is exercised by the new concurrent-category test (→ Documents). All three previously-committed-but-unused fixtures are now uploaded and asserted per the fixtures README. The offline test additionally asserts the People-vs-Nature priority at unit level.
8. **Three more ACs covered:** (a) two near-simultaneous uploads mapping to one brand-new category (Documents) assert exactly ONE folder row + `photoCount: 2` + neither job crashes (P2002 catch-and-refetch exercised live — the constraint violation is visible in the worker log when the race actually fires); (b) `GET /api/photos/:id` `exif` object asserted both ways — all-null for a no-EXIF noise fixture, and populated `cameraMake`/`cameraModel` for a sharp-`withExif`-tagged upload round-tripped through the worker's exifr pass; (c) reclassify limiter independence: structural assertion (`reclassifyRateLimiter` is a distinct middleware instance/store from `uploadRateLimiter`) **plus** a behavioral test — a fresh user exhausts the reclassify bucket (30× 404 then 429) and uploads + logins still succeed. Note: the auth limiters are module-private in `routes/auth.ts` and disarmed under `NODE_ENV=test` (limit 1000), so *auth-side* bucket exhaustion is impractical from the suite — its independence is proven behaviorally in the login-after-429 direction only, plus the pre-existing auth-split test.
9. **Offline-classification AC now has recorded verification** (was previously asserted without evidence — see Testing notes below for method + result), and it's committed as a permanent test (`src/__tests__/classification.offline.test.ts`), not a one-off.

## Finding #1 follow-up (2026-07-02 re-verification): circular duplicates survived through the pHash phase — now closed

Re-verification of finding #1 showed the symmetry-breaker fix was applied to the **SHA-256 phase only**. The pHash phase-2 candidate query had **neither** the `duplicateOfPhotoId: null` exclusion **nor** the strictly-older constraint, and the duplicate-marking update persisted the duplicate's own `phash` in the same write — so the cycle re-formed through a mixed sha256/phash edge pair.

**Verified repro (timing-dependent at worker concurrency 2; deterministic when A's first attempt transiently fails and BullMQ retries):** upload identical non-flat bytes twice, A older / B newer, with B's job completing before A's phase-2 scan. (1) B sha256-dedups against A and commits `phash=P`; (2) A's exact pass finds nothing strictly older; (3) A's phase-2 scan returns B (phash set, no duplicate exclusion), hamming(P,P)=0 → A marked `duplicateOfPhotoId=B`, `dedupMethod=phash`. Result: A→B (phash) + B→A (sha256), both stuck `status=duplicate`, no folder, never classified.

**Fix — belt and suspenders, all three layers (each independently kills the cycle):**

1. `duplicateOfPhotoId: null` added to the phase-2 candidate query — a row already marked duplicate can never be an "original".
2. The same strictly-older constraint phase 1 uses (`createdAt < mine`, OR `createdAt == mine AND id < mine`) added to phase 2 — **all** dedup edges, sha256 and phash alike, now point strictly backwards in ONE total order `(createdAt, id)`, so no mix of edge types can form a cycle. (Key supporting invariant: each job writes its own phash only *after* its own scan, so with 1+2 in place a candidate with a committed phash is always a fully-scanned, strictly-older non-duplicate.) Phase 2 also gained a deterministic `orderBy` (oldest match wins), matching phase 1's canonical-original semantics.
3. **Choice on phash persistence: rows marked duplicate no longer persist a phash — explicitly `phash: null` in the duplicate-marking update** (not merely omitted, so a BullMQ retry that flips a previously-non-duplicate attempt's verdict can't leave a stale phash behind either). Why this option over "keep persisting since 1+2 make it safe": a duplicate row's phash is dead weight (with layer 1 in, no query may ever read it), and nulling it means even a *future* query that forgets the invariant's exclusions structurally cannot match a duplicate row in the pHash pass — cheap defense-in-depth. Accepted trade-off: if a duplicate is later rescued via reclassify (which clears the verdict but never re-runs dedup), that photo carries no phash and can only be matched by *future* uploads via the SHA-256 exact pass, not near-dup — acceptable because the strictly-older original still carries the phash and remains the canonical near-dup target.

**Implementation shape:** both candidate scans extracted from `worker.ts` into `backend/src/lib/dedup.ts` (`findExactDuplicateOriginal` / `findNearDuplicateOriginal`) so the production queries are directly unit-testable; the invariant is documented at the top of that module ("all dedup edges point to strictly-older, non-duplicate photos — cycles structurally impossible") and referenced from the worker. Worker step 3 behavior is otherwise unchanged (hard gate before `classify()` intact, degenerate flat-image guard intact, per-user scoping intact); as a side effect, sha256-detected duplicates now skip the pHash computation entirely (it was computed and then only used for the write we removed).

**Regression test (deterministic, not a race):** `backend/src/__tests__/dedup.regression.test.ts` (new, 7 tests, DB-only, skips gracefully without Postgres). A full-race e2e would be timing-dependent and flaky, so instead the suite constructs the exact DB state the race produces (B newer, duplicate-of-A, phash committed) and runs the real `lib/dedup.ts` queries against it: the repro state itself (A's scan must return null; B's edge still points backwards only), each invariant constraint isolated (strictly-newer non-duplicate excluded; older-but-duplicate excluded in favor of the canonical original), the `(createdAt, id)` tiebreak in one direction only, per-owner scoping, the degenerate flat-hash guard, and the phase-1 oldest-canonical/no-backwards-edge behavior. Tests share one owner, so each uses its own phash value with pairwise hamming distance ≥ 32 (asserted by a sanity test) to prevent cross-test pollution.
