## Title

chore: bump next + eslint-config-next 14.2.13 → 14.2.35

## Description

`frontend/package.json` pinned `next` and `eslint-config-next` at `14.2.13`, which `npm audit` flagged for a large batch of CVEs including one **critical** (authorization bypass). This bumps both — kept in lockstep as they already were — to `14.2.35`, the latest patch on the **`next-14` dist-tag** (i.e. the current 14.2.x line).

This is deliberately a patch bump, **not** a major migration. Jumping to Next 15/16 (which `npm audit fix --force` would do) is a breaking change and is explicitly out of scope for this pass — see "Follow-up decision for Abhishek" below.

**No application source was touched.** The only changed files are `frontend/package.json` (two version pins) and `package-lock.json` (regenerated by `npm install` from the repo root — this is an npm-workspaces monorepo, so the lockfile lives at the root). `next build` under 14.2.35 required zero code fixes.

### Transitive advisories — status unchanged, deliberately not force-fixed

- **`glob` (high) — `GHSA-5j98-mcp5-4vw2`** — command injection via the glob CLI's `-c`/`--cmd` flag (`shell:true`). Reaches us transitively: `eslint-config-next` → `@next/eslint-plugin-next` → `glob`. This is a **build-time-only dev dependency** and the vulnerability is only exercised if you invoke the `glob` CLI with untrusted input, which nothing in this project does — it is non-reachable in our usage. Its only npm-offered fix drags in `eslint-config-next@16.2.10` (breaking). Left as-is.
- **`postcss` (moderate) — `GHSA-qx2v-qp2m-jg93`** — XSS via unescaped `</style>` in CSS stringify output. Transitive under `next`. Its only npm-offered fix drags in `next@16.2.10` (breaking). Left as-is.

`npm audit fix --force` was **not** run (it installs `next@16.2.10` / `eslint-config-next@16.2.10` — a breaking major). No force-fix of the transitive items either.

## Follow-up decision for Abhishek (flagged, NOT actioned)

A full `npm audit` clear (the 14 remaining `next` advisories + the `glob` and `postcss` transitive items) requires a **Next 15 → 16 major migration**. That is a breaking change — App Router API surface, `useSearchParams`/RSC semantics, the config format, and the ESLint config all shift across those majors — and is out of scope for this hardening pass. It is a separate, explicit decision for Abhishek: whether/when to schedule a Next major-migration cycle. This MR intentionally does not attempt it; it captures the risk-reduction available *without* breaking anything.
