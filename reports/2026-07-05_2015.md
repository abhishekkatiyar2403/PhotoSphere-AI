## New Failures

### [HIGH] Wrong OTP redirects the owner off `/guests` instead of showing "Invalid code"
- **Steps to reproduce:**
  1. As an owner, create a share and have a guest request access (pending request appears on `/guests`).
  2. On `/guests`, type a **wrong** 6-digit code into the pending request's OTP input.
  3. Click Approve.
- **Expected:** an inline error on the request card ("Invalid code" / similar); the owner stays on `/guests` and can retry (the backend correctly enforces up to 3 attempts → auto-deny).
- **Actual:** the owner is **redirected away from `/guests`** — `router.replace("/login")` fires, and since the owner still has a valid session, `/login` bounces them on to `/dashboard`. No "Invalid code" feedback is ever shown; the owner loses their place in the approval flow. (Screenshot `reports/screenshots/2026-07-05_2010-owner-bounced-off-guests.png` shows the owner landed on the Dashboard after a wrong OTP.)
- **Root cause:** `frontend/src/app/guests/page.tsx` `handleApprove` catch block treats **any** `ApiError` with `status === 401` as a session-auth failure (`if (isAuthError(err)) { router.replace("/login"); return; }`). But the backend returns **`401 "Invalid code"`** for a wrong OTP (confirmed live: `POST /api/access-requests/:id/approve` with a wrong code → `HTTP 401 {"error":"Invalid code"}`, matching `specs/guest-access-otp.md` line 189). A wrong OTP is a business-logic response, not an auth failure — conflating the two is the bug. This is the primary interaction on the page and it breaks on the very first mistyped digit.
- **Suspected area:** `frontend/src/app/guests/page.tsx`, `handleApprove` (the 401→`/login` branch). The fix is to NOT treat a 401 from the approve call as an auth redirect — surface `err.message` inline like the other error paths already do. (The `isAuthError` redirect is appropriate for the page-load/`load()`/revoke paths where 401 genuinely means "session gone", just not for OTP approval.)
- **Why the Developer's live check missed it:** the MR draft's verification only ever entered the **correct** OTP; a mistyped code was never exercised.

### [MEDIUM] Already-approved re-visit 404s — the `already_approved` short-circuit is unreachable on a single-use invite
- **Steps to reproduce:**
  1. Guest requests access, owner approves, guest reaches `unlocked` (guest session cookie set).
  2. Guest re-opens `/g/:token` and clicks "Request access" again.
- **Expected (per spec decision G10):** a live guest session exists → backend returns `{ status: "already_approved" }` → the portal short-circuits straight to `unlocked` (the frontend already handles this response at `g/[token]/page.tsx` lines 98–102).
- **Actual:** the re-request returns **`404 "Invite not found"`** (confirmed live over HTTP, guest cookie present); the portal shows "This invite link is invalid or has expired." and stays on `landing`. The `already_approved` branch in the frontend is effectively dead code.
- **Root cause — a collision between two of the spec's own decisions:** the invite is `max_uses = 1` (G6), and approval increments `use_count` to 1 (`backend/src/routes/accessRequests.ts:153`). On the next `POST /:token/request`, `backend/src/routes/invites.ts` checks `use_count >= max_uses` (line 140) and 404s (line 143) **before** the live-session `already_approved` check (line 155). The spec's API-contract table (line 196) literally orders the exhaustion-404 check first, so the Developer built it faithfully — but that ordering makes G10's "live session → already_approved" path unreachable for exactly the case it was meant for. No data loss: the already-approved guest still holds a valid guest-session cookie, so direct `/api/guest/*` access still works; only the re-visit-through-the-link UX is broken.
- **Suspected area:** `backend/src/routes/invites.ts` `POST /:token/request` (check ordering) OR a frontend re-attach that doesn't rely on re-requesting. **This is a spec-question as much as a bug** — flagging for Master/Planner: either move the `already_approved` check ahead of the exhaustion-404, or the frontend should detect an existing guest session another way on re-visit. Needs a decision, not a silent code change.
