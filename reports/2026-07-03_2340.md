## Investigated non-bug (recorded per "no fabricated test results")

### [Not a bug — test-classifier scope gap] Auth-flow "3 genuine errors" were pre-login auth-gate 401s

- **What happened:** The auth-flow test's error classifier flagged `genuine=3` on the first tightened run.
- **Root cause (confirmed by logging every non-benign response):** the three were `401 GET /api/dashboard`, `401 GET /api/collections`, and `401 GET /api/photos/unfiled` — the dashboard page's three data-assembly fetches firing during the brief pre-authenticated window on the initial load / login transition, before the session cookie is established. The client's auth gate then redirects to `/login`. This is the **identical benign auth-gate pattern** every page has used since Week 1-2 (the `authApi.me()` → redirect flow), and it's the exact artifact prior reports (2026-07-03 19:02, 00:50) explicitly flagged and warned against misattributing (they'd whitelisted only `/api/auth/me`; the dashboard fires three *more* gated GETs of the same class).
- **Re-verified clean two ways:** (1) an isolated load of `/dashboard` **with a valid cookie from first paint** produced **0** of these 401s, **0** pageerrors, **0** hydration/console errors; (2) the Dashboard-populated and Dashboard-empty blocks (which set the cookie before navigating) both passed the genuine-error check at 0. The 401s only appear when the page is deliberately loaded pre-auth — i.e. the gate doing its job. **Not a Next 14.2.35 regression, not a bug.** Corrected verdict: 53/53 app-clean.

*(For the record: an earlier, looser pass this cycle also tripped on the browser's "Failed to load resource: 400" console line emitted by the deliberately-rejected bad-magic-bytes upload, and on a stale seed-time count snapshot vs. a live dashboard re-fetch. Both were harness artifacts — the 400 is the app correctly rejecting a bad file, and the count "mismatch" was my oracle captured before worker jobs settled. Both were corrected: the classifier now excludes the deliberate 400, and the dashboard assertions now use a live API oracle re-fetched at render time. Neither is an app defect.)*

## Methodology / process notes

- **Seeded via the real API + live worker, not DB fixtures.** Two users: a populated user (photos across 4 real folders — Animals/Food/People/Vehicles — plus a `FORCE_FAIL_` failed photo and a byte-identical sha256-duplicate, both landing in the Unfiled bucket) and a fresh/empty user. The populated user's dashboard/folder/unfiled truth was read from the raw `GET /api/dashboard` etc. and used as the assertion oracle; the dashboard block re-fetches it live at render time to avoid a stale-snapshot race.
- **Test images: sharp-generated, visually distinct, unique per run.** Prior attempts appended random trailer bytes to a single base JPEG — those share an identical *perceptual hash*, so the pHash near-dup pass correctly flagged all but the first as duplicates (this is the pipeline working, not a bug — the exact methodology trap prior reports flagged: derive expectations from real bytes, not fixture names). Switched to `sharp`-rendered noise images with per-image low-frequency patterns so they don't pHash-collide, then tuned each one's sha256 bucket (via a small trailer) to land in the intended folder. Magic bytes stay `FF D8 FF` throughout.
- **Bad-magic-bytes fixture** is a real Windows PE header (`4D 5A 90 …`) renamed `.jpg` — genuinely rejected by the content sniffer regardless of extension.
- **XHR progress bar** was verified under CDP upload throttling (200 KB/s) with a larger file, sampling `<progress value>` every 30 ms — a plain local upload finishes too fast to observe intermediate values, same reasoning as the 02:27 report's methodology note. Intermediate (0,1) values were observed.
- **Signup rate limit (5/15min/IP, Pending Decision 6) was hit hard during seeding** — the second (empty) user's signup took ~630s of 30s-interval retries to clear a freed window. Handled honestly with a wait loop; no server restart, no fabrication. This is the same single-IP test-account-creation friction every prior report has noted; not a defect. It added real wall-clock time to this run.
- **Console-error classification** distinguishes genuine client errors (pageerrors, hydration/React/Next warnings, unexpected ≥400 responses) from two known-benign classes (pre-login auth-gate 401s; the deliberately-tested bad-upload 400). Genuine errors are the real signal a framework bump would produce — there were none.
- Test users (`nxpop_*`, `nxempty_*`, `nxui_*`, `nxauthd_*`, `nxcookie_*`, `nxexif_*`, all timestamped `@example.com`) were not cleaned up — throwaway scratchpad accounts, no sensitive data, consistent with every prior report.
- All scripts/fixtures/results live in the session scratchpad (`next-regress/`), not committed. Screenshots saved to `reports/screenshots/2026-07-03_next-*.png`.
- **MinIO/DB console access skipped on principle**, consistent with every prior report.
