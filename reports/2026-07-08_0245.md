## Priority 0 — the intermittent flake investigation

**Reproduction attempt: 9 runs total this session** (7 full 13-file suites via `npm test`, 2 near-full 8-file subsets via `npx vitest run <8 files>` including `guest-access.smoke.test.ts` alongside `classification.smoke.test.ts`, `dashboard.smoke.test.ts`, `audit.smoke.test.ts`, `trash-system.smoke.test.ts`, `search.smoke.test.ts`, `folder-mgmt.smoke.test.ts`, `folder-zip.smoke.test.ts`).

**Result: 8/9 runs fully clean (173/173 on full runs, 144/144 on the 8-file subset). 1/9 runs failed — but NOT the assertion Abhishek reported.**

The one failure this session was:
```
FAIL src/__tests__/classification.smoke.test.ts > auth rate-limit split (carry-over a) >
  does not 429 repeated logins under NODE_ENV=test (buckets relaxed, suite re-runnable back-to-back)
Error: Test timed out in 5000ms.
```
This test does 8 sequential `POST /api/auth/login` calls (each doing a bcrypt compare — CPU-expensive) with **no explicit timeout override**, so it inherits vitest's default 5000ms `testTimeout`. Under the full 13-file concurrent suite it occasionally can't complete 8 sequential bcrypt-gated HTTP round-trips in 5s. This is a **pre-existing fragility** (already flagged once before — STATUS.md's `docs: log rate-limit test flakiness` commit predates the trash-system work entirely) unmasked by the suite getting heavier (`137 → 173` tests, +2 new files), not something the trash-system change introduced.

**The specific guest-access 404 Abhishek described did NOT occur in any of my 9 runs.** I cannot confirm, deny, or root-cause it today — it is a genuine intermittent (his 4 runs: 2/4 fail; my 9 runs: 0/9 reproduce that specific assertion) and coin-flip-style flakes on shared infra are exactly the kind of thing that can go quiet for a session and come back later depending on machine load, other processes, GC pauses, etc.

**What I checked to build/refute the theories, without a live repro to test against directly:**

1. **`getPermittedFolderIds` (the choke point) — read in full.** It is a single Prisma query per call, no caching, no memoization, `revokedAt: null` + `expiresAt` OR + the new `folder: { deletedAt: null }` filter, all evaluated by Postgres in one round trip. There is no in-process state that could go stale between the owner's `approve` call and the guest's next request — every call re-queries the DB directly. This makes a **pure application-level cache-staleness race very unlikely** as the mechanism.

2. **Read-after-write visibility across pooled connections.** Postgres uses MVCC with READ COMMITTED as the default isolation level (nothing in `prisma/schema.prisma` or `src/lib/prisma.ts` overrides this). Under READ COMMITTED, once a transaction commits, every subsequent transaction on any connection sees the committed data immediately — there is no "the second connection hasn't caught up yet" window the way there can be under async replication. This makes the specific "session write not yet visible to the very next request" framing unlikely to be a plain visibility bug, UNLESS the approve endpoint's session/permission writes and the guest's OWN session creation are not fully committed before the HTTP response is sent (see #4 below — this is the one lead I could not fully rule out without a live repro).

3. **Connection pool exhaustion — real contention confirmed, but no direct evidence it caused this specific failure.** No `connection_limit` parameter is set on `DATABASE_URL` in `backend/.env`, so Prisma defaults to `num_cpus * 2 + 1` per `PrismaClient` instance. This machine has **10 CPUs → 21 connections per client**. Vitest's default `threads` pool runs each of the 13 test files as a separate worker with its own module registry, meaning up to **13 separate `PrismaClient` singletons could each open up to 21 connections** — a theoretical worst case near 273, well over Postgres's configured `max_connections = 100`. I confirmed genuine write contention exists under the full suite: run 3 this session logged multiple `"Transaction failed due to a write conflict or a deadlock. Please retry your transaction"` Prisma errors (these are internally retried and did not fail any test), and `pg_stat_activity` showed 11-12 concurrent connections mid-run (well under 100 in my observed samples — but I only sampled twice, not continuously, so I cannot rule out a brief spike near the accepted 5s timeout window). **This is circumstantial, not proven** — I did not catch the pool anywhere near exhaustion in my direct samples, but the absence of a `connection_limit` override combined with 13-file concurrency is a real, unaddressed structural risk regardless of whether it's THIS bug's cause.

4. **The most plausible mechanism I could NOT rule out:** the approve endpoint does two separate write operations in sequence — hashing/verifying the OTP and updating `AccessRequest.status`, then (on the guest's subsequent poll, per the G7 mechanism) creating the `GuestSession` row via `createGuestSessionFromHash`. If these are not wrapped in a single transaction and the test's `poll` request races the connection pool under heavy concurrent load (a connection checkout delay, not a data-visibility issue), the guest's session could be issued correctly but a *downstream* request on a **different, slower-to-acquire connection** could theoretically observe an inconsistent intermediate state if any part of the guest-folder-permission chain spans multiple non-atomic writes. I read `src/lib/guestSession.ts`'s `createGuestSessionFromHash` and it is a single `prisma.guestSession.create()` call — atomic by construction, so this specific step is not the culprit. I did not have a live failure to attach a debugger/query-log to, so I cannot go further than this without either (a) a live reproduction, or (b) instrumenting query timing under load, which risks fabricating a root cause I can't back up.

**Verdict on Priority 0: INCONCLUSIVE, reported honestly.** Safe-direction is very likely correct (a false-404 hiding something that should be visible, never a leak) based on the described symptom, though I did not personally observe the failure to confirm this firsthand this session. I did NOT find evidence this is a NEW race introduced specifically by the trash-system change (`folder: { deletedAt: null }` is a simple, non-blocking additional WHERE clause on an existing single-round-trip query — it doesn't introduce any new write, lock, or cross-request dependency). My best-supported hypothesis, if forced to rank: **generic connection-pool/CPU contention from running all 13 files fully in parallel with no `connection_limit` tuning and default 5s test timeouts**, which is a pre-existing structural gap in the test setup (confirmed unrelated flakiness reproduced this session in a completely different file/assertion) that the suite growing to 173 tests makes more likely to surface, rather than something specific to the guest-access approve→poll→list flow or the trash schema change. Recommend Developer/Master: (a) set an explicit `connection_limit` on the test `DATABASE_URL` sized to the actual concurrency (e.g. `connection_limit=5` per file × 13 ≈ 65, safely under 100), and/or (b) add a `vitest.config.ts` with a higher global `testTimeout` (the rate-limit carryover test's 5000ms default is demonstrably too tight under full-suite load) — both would reduce generic flakiness whether or not they turn out to be THIS specific bug's cause. Do not treat this write-up as a confirmed root cause — it is a ranked, honest theory, not a proof.
