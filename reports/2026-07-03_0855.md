## Methodology / process notes

- **This was explicitly scoped as a focused fix-verification, not a full regression** — per the task brief. Areas outside the fix's blast radius (auth, upload pipeline, dashboard-stats, most of the AI-classification organizing layer) were not re-run live this cycle; they were last confirmed clean in `reports/2026-07-03_0731.md` and by Master's independent backend-suite/typecheck/lint confirmation on this exact commit.
- **Test 2 (the duplicate variant) was deliberately built stronger than the Developer's own new test for the same scenario.** Reading `backend/src/__tests__/classification.smoke.test.ts`'s new `describe` block directly, its own code comment admits the "duplicate of nothing-yet-classified" test actually uses a first upload that *succeeds* (creating a collection), then treats a second, unrelated fresh user's dup-of-itself as a stand-in — explicitly noting a true "first-ever upload is itself a duplicate before any collection exists" case wasn't achieved server-side in that test. This report's Test 2 closes that gap: both uploads are `FORCE_FAIL_`-prefixed, so the base photo never classifies successfully and no collection is ever created for either photo — confirmed against `lib/dedup.ts`'s documented invariant (a valid dedup candidate need only be non-duplicate and strictly older, not previously *successful*) before relying on it, rather than assuming it would work.
- **Signup rate-limit budget (5/15min/IP, live/unrelaxed under `NODE_ENV=development`) was the dominant cost of this session.** Wall-clock cost from rate-limit waits: roughly 45 minutes across three separate reset windows (one for the main Test 1+2 pass, one that partially exhausted mid-Test-4/5, one final wait for Test 5's cross-user isolation after Test 4 consumed the remaining budget). All waits used a real until-loop against the live `RateLimit-Remaining` header (backgrounded, not blind sleeps) rather than fixed-duration guesses — following the prior report's own documented lesson. One self-inflicted early mistake, caught and corrected: a wait-loop's own threshold check (`>= 5`) could never be satisfied because every probe that lands in a fresh window immediately consumes one of the 5 slots for itself, permanently capping the observed remaining count at 4 — fixed by lowering the threshold to `>= 3`, leaving headroom for the batch about to run.
- **Batch splitting was necessary and is reflected in the numbering above but not in separate "batch" language in the results tables** — all 30 numbered checks ran against the same live dev stack/commit, just across three separate script invocations (`batch1.js` for Tests 1–3, `batch2.js` for Test 4 + Test 5's 401 check, `batch3_t5only.js` re-running Test 5 in full after `batch2.js` hit the rate limit mid-test on User A's signup). No test was skipped or faked to work around the rate limit — the partial `batch2.js` run's Test 5 results were superseded by the complete `batch3_t5only.js` run, not merged inconsistently.
- **`data-testid` selectors were used in preference to text-content regex matching** (`[data-testid="folder-row-Unfiled"]`, `[data-testid="folder-row-${folderName}"]`) after reading `frontend/src/app/organize/page.tsx` directly and finding these attributes already present — more reliable than a text match, and confirms the Developer left good hooks for future automated frontend testing (still no committed frontend test suite in this repo, same gap noted in every prior report).
- **MinIO/DB console access skipped on principle**, consistent with every prior report.
- **Housekeeping, unchanged from prior reports:** the stale duplicate `tsx watch src/server.ts` process (PID 15469, `Wed08AM` start time) is still running alongside the live pair (PIDs 86817/86224) — benign (only one can bind :4000), flagged for the third consecutive report now, worth actually killing next time someone's at the machine.
- Test users created during this session (all `t1_/t2_/t4_/t5_*` prefixed, timestamped) were not explicitly cleaned up via `afterAll` (this was a hand-authored scratchpad script, not a committed test file) — flagging for anyone doing a DB-level audit later; none of these accounts contain anything sensitive, all are throwaway `@example.com` addresses matching the pattern used in every prior report's manual verification.
