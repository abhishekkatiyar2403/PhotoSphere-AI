## Methodology note (not a bug, but a real interaction worth flagging)

**Shared IP-keyed rate-limit bucket across `/api/auth/signup` and `/api/auth/login`.** The same `authRateLimiter` instance (5 requests / 15 min, keyed by `req.ip`, no `trust proxy` config) is applied to *both* signup and login routes (`backend/src/routes/auth.ts` lines 17–23). This is not a violation of the spec as written — the spec only says "rate limiting on `/api/auth/login` and `/api/auth/signup`," and 5/15min shared across both is a legitimate reading of that. But it has a real practical consequence for local testing (and worth knowing about for real usage too): a normal developer or QA session that does a handful of signups followed by a couple of login attempts within a 15-minute window can trip 429s well before hitting 5 login attempts specifically, because signup attempts consume the same bucket. During my first pass at this suite, running ~14 signup/login calls back-to-back (a realistic "someone testing the feature manually" pattern) caused cascading 429s partway through, which I initially had to isolate before confirming the underlying auth logic itself was correct. I restarted the backend (`touch backend/src/server.ts`, which `tsx watch` picks up — a benign, reversible action, not a code change) between test groups to get a clean rate-limit bucket for each; that is a valid workaround for testing but not something an end user gets. **This is worth a product decision, not a code fix from me:** consider whether signup and login should have independent rate-limit buckets (most SaaS products do — a burst of signups shouldn't lock out a legitimate login attempt from the same IP, e.g. shared office/NAT IPs), or whether the current shared-bucket behavior is intentional. Flagging as a question for Planner/Developer rather than filing it as a bug, since the spec's acceptance criteria are satisfied exactly as written.

## Data-layer spot check (partial — one query blocked)

- `sessions` table inspected directly in Postgres: `token_hash` values are 64-character hex strings (consistent with SHA-256 output, matching `hashToken()` in `backend/src/lib/session.ts`), never plaintext tokens. `revoked_at` is correctly `NULL` for active sessions and populated with a timestamp for the session I logged out during testing — confirms server-side revocation is real, not just a cookie-clear on the client.
- I did **not** query `users.password_hash` directly — that specific query was blocked by the environment's auto-mode permission classifier as unnecessary credential-material exposure into the transcript, and I did not attempt a workaround (e.g., piping through another tool) since the restriction is reasonable and the same conclusion (passwords are bcrypt-hashed, never plaintext) is already strongly evidenced indirectly: login only succeeds with the exact correct password across all test cases, wrong passwords always fail, and the signup/login code path (reviewed directly) calls `bcrypt.hash`/`bcrypt.compare` with cost factor 12 and never stores or logs the raw password. If Abhishek wants a direct DB spot-check of `password_hash` values for extra assurance, that needs an explicit one-off permission grant or should be done manually outside this agent loop.
- JWT-negative check: session tokens are 64-char hex strings (`crypto.randomBytes(32).toString("hex")`), structurally incompatible with a JWT (which requires three base64url segments separated by `.`) — confirmed both by code inspection and by the raw token format observed in the `sessions.token_hash` column (the hash of the same format). `grep -ri jwt backend/src` was not re-run by me this pass (Developer already reported it returns nothing) but no JWT library appears anywhere in `backend/src/lib/session.ts`, `routes/auth.ts`, or `middleware/requireAuth.ts`, which I did read directly.
