## New Failures

### [Not a bug — test-fixture artifact] Image-resolution check initially failed due to a wrong-sized test fixture

- **What happened:** Test #17's dimension check was first run against `nature-0.jpg`, one of three custom fixtures generated for the Prev/Next multi-photo test. That generation script created 64×64 images (matching the size convention used by the repo's own committed classification fixtures), not realizing the same images would later get reused for the resolution check. The check failed as "64×64 instead of 800×600" — which is exactly what a correctly-working thumbnail-vs-original bug would also look like, so it had to be run down rather than dismissed.
- **Root-caused, not assumed:** confirmed via `sharp('nature-0.jpg').metadata()` that the source file itself is 64×64 — i.e. the pre-signed URL correctly served the original at its true (small) resolution; the app did nothing wrong.
- **Independently re-verified clean:** re-ran the identical check end-to-end (fresh signup, fresh upload, fresh browser session) against `exif-full.jpg`, an 800×600 source image, in isolation from the rest of the suite. Result: `img.naturalWidth/naturalHeight` = exactly 800×600, and the `src` was confirmed to be the real pre-signed `original.jpg` URL (`X-Amz-Expires=60`, matching the documented 60-second TTL), not a `thumb_` key. Test #17 above reflects this corrected, passing run.
- **Disposition:** not counted as an app bug. Flagged here in full rather than silently fixed and re-run, per "no fabricated test results" — the initial failure and its resolution are both part of the record.

## Methodology / process notes

- **EXIF fixtures had to be built from scratch, not reused from the repo.** The only committed/in-repo EXIF-tagged test image (in `classification.smoke.test.ts`) covers Make/Model only, explicitly noting `takenAt`/GPS were never populated. Since the spec's acceptance criteria and this task explicitly require testing a photo with "real EXIF (camera make/model/GPS/taken-at all populated)," two new fixtures were generated: `exif-full.jpg` (full EXIF via `piexifjs` raw byte injection — `sharp`'s own `withExif()` in the installed 0.35.3 version was tried first and confirmed, empirically, to only reliably persist `IFD0` tags, silently dropping `ExifIFD`/`GPSInfo` — this was caught by parsing the sharp-generated file with `exifr` immediately after generating it and finding `DateTimeOriginal`/GPS absent, before ever using it in a real test) and `exif-none.jpg` (a flat-color JPEG with zero EXIF segment). Both were independently verified against `exifr.parse()` — the exact library and options (`{ gps: true, tiff: true, exif: true }`) the worker itself uses in `worker.ts` — before being trusted as valid test inputs, so the EXIF panel tests are checking real parsed worker output, not assumptions about what the fixture contains.
- **Three additional flat-color fixtures (`nature-0/1/2.jpg`) were generated and pre-verified to land in the same mock-classification category** (brute-forced against the mock's actual `sha256(bytes)[0] % 7` logic, read directly from `backend/src/lib/classification/index.ts`, rather than guessed) so a genuine 3-photo single folder existed for the Prev/Next tests — this is also the source of the one initially-failing test above.
- **Network-level read-only verification used Playwright's `page.on("request")` listener** rather than only the DOM-absence checks the MR draft itself performed, giving an independent, harder-to-fool confirmation that clicking around `/browse` truly never triggers a mutating call — not just that no button exists to trigger one from this particular click path.
- **The backdrop-click-to-close fix (the one bug the Developer found and fixed on itself before handoff) was treated with the same skepticism the task explicitly asked for** — re-tested from a cold state (fresh viewer open, click at literal viewport corner coordinates) rather than trusting the MR draft's own "re-verified live after the fix" claim, plus an additional sanity check (clicking directly on the image does NOT close it) to confirm the fix's click-target guard is discriminating correctly, not just accidentally closing on every click.
- **`/organize`'s Move and Reclassify were re-verified functionally, not just confirmed present in the DOM**, per the task's explicit instruction — Move was checked via a real folder-count reconciliation against the backend, and Reclassify via polling the backend status endpoint directly to confirm the photo actually reached `done` with a real `folderId`, rather than trusting a UI-only signal.
- **Console/page-error monitoring was active throughout the exploratory/stress-test portion** (rapid clicking, alternating nav spam) — zero errors surfaced, which is meaningful given that race conditions in rapid-fire UI interaction are exactly the kind of thing that produces silent console errors without visibly breaking the page.
- **Browser-back-button behavior (exploratory item #57) is recorded as expected-per-spec, not a bug** — `specs/week7-8-dashboard-browser-viewer.md`'s Photo viewer section and Open Question 3 explicitly default to "no URL/route for the open viewer state this pass... closing the tab or navigating away simply loses it" — the observed behavior (back navigates the whole page away, viewer state lost) is the documented, accepted trade-off, not a defect. Still flagged in Notes below since it's a real UX rough edge worth Abhishek's awareness even though it's not a bug against the current spec.
- **MinIO/DB console access skipped on principle**, consistent with every prior report.
- **Housekeeping, unchanged from every prior report today:** the stale duplicate `tsx watch src/server.ts` process (PID 15469, `Wed08AM` start time) is still running alongside the live pair (PIDs 86817/86224) — benign, flagged for the fourth consecutive report now, worth actually killing next time someone's at the machine.
