## New Failures

### [High] First-ever failed/duplicate photo is permanently unreachable in the Organize UI until a *different* upload succeeds

- **Steps to reproduce:**
  1. Sign up a brand-new user who has never had a successful classification.
  2. Upload exactly one photo, named with the `FORCE_FAIL_` prefix (or a byte-identical duplicate of nothing — any path that resolves to `failed`/`duplicate` on the very first classification attempt works identically).
  3. Poll `GET /api/photos/:id/status` until it reaches `failed` (confirmed live: reached `failed` at ~6.6s, `folderId: null` throughout).
  4. Immediately `GET /api/collections` for this user → returns `{"collections": []}` (empty — no default "My Photos" collection exists yet, because the worker only lazily creates one at the *folder-assignment* step, which a failed job never reaches).
  5. Load `/organize` in a real browser as this user.
- **Expected:** The photo is `failed` and genuinely exists; per the spec's own requirement that failed/duplicate photos be "reachable and actionable," and per the Unfiled mechanism's own design intent, it should appear under an "Unfiled" row with a working Reclassify button.
- **Actual:** The sidebar shows **"No folders yet — upload a photo to get started, or create one below."** No "Unfiled" row renders at all. The main panel shows "Select a folder to view its photos." There is no way to reach or reclassify this photo from the UI — a user in this exact (very plausible) situation is completely stuck, despite the photo, its failure state, and its data all being real and confirmed via direct API calls. Screenshot: `reports/screenshots/2026-07-03_0730-organize-unfiled-not-reachable-before-first-collection.png`.
- **Confirmed not a flake / confirmed the actual boundary:** uploading a second, *successful* photo for the same user (which lazily creates the default collection at that point) immediately makes the original failed photo visible under a now-rendering Unfiled row on the very next page load — proving the Unfiled mechanism itself is correct, and the bug is specifically the initial-load code path bailing out entirely when `GET /api/collections` returns empty, without ever falling back to checking for unfiled photos independently of collection existence.
- **Root cause (read directly, `frontend/src/app/organize/page.tsx` lines 143–169):** the initial-load effect does `const res = await collectionsApi.list(); ... if (!defaultCollection) { setFoldersLoading(false); return; }` — it never calls `unfiledPhotosApi` in this branch, and `unfiledPhotosApi.list()` itself requires a `collectionId` in its URL (`GET /api/collections/:id/unfiled-photos`), so there is no code path today that can surface unfiled photos before a collection exists at all. The existing inline comment ("No collection yet ... not an error, just an empty state") is accurate only for a genuinely-brand-new user with zero uploads; it doesn't account for a user whose only uploads so far all failed or deduped.
- **Suspected area:** `frontend/src/app/organize/page.tsx` (initial-load effect) and, if a backend-side fix is preferred instead, `backend/src/routes/collections.ts`'s `unfiled-photos` route (currently keyed by an existing collection id — could instead be scoped purely by `ownerId` at a route not requiring a collection id, since the route's own code comment already notes `ownerId` is the real scoping mechanism and collection id is only used for the ownership check).
- **Likelihood in practice:** genuinely plausible, not a contrived edge case — any real user whose first-ever upload happens to fail classification (a real Vision API call failing, a corrupt file, a transient worker error) or happens to be a duplicate of nothing-yet-classified would hit this. It is a coincidence of test ordering, not app behavior, that the task's own suggested step order ("upload enough fixtures to populate at least 2 real folders" before touching Unfiled) avoids ever exercising this path.
- **Not a regression** — this is new surface introduced by this build, not a previously-passing behavior that broke.

## Methodology / process notes

- **Given the explicit instruction to apply extra scrutiny to this build** (interrupted Developer session, no safety-classifier review pass), I did not stop at re-deriving the MR draft's own manual-verification claims — all of which held up exactly as claimed — but spent additional time on exploratory sequencing the task's own suggested steps didn't cover (uploading a failure/duplicate case *before* any successful classification, rather than after). That is what surfaced the High-severity bug above. Flagging this explicitly since it's the kind of gap a reduced-review cycle is most likely to miss: the feature works correctly for every order of operations the spec/task happened to describe, but not for a materially different (and more realistic, for a brand-new real user) ordering.
- **Test-harness false failure, caught and corrected before trusting it:** my first version of the cross-user-isolation test (unauthenticated 401 check) used Playwright's shared `request` fixture, which automatically stores `Set-Cookie` responses in its own cookie jar — since an earlier line in the same test signed up "User B" via that same fixture, the supposedly-cookie-less request silently carried User B's session and returned 404 instead of 401. Confirmed via a raw `curl` with genuinely no cookie that the live endpoint correctly returns 401 — this was a test-script bug, not an app bug. Fixed by using a fresh, isolated `APIRequestContext` for that specific check. Flagging as a reusable gotcha: **Playwright's `request` fixture is not cookie-isolated across sequential calls within a test** the way per-test browser contexts are; explicit `Cookie` headers on other calls override the jar, but a call with *no* explicit header will silently inherit whatever the jar last received.
- **Pagination >12 photos required generating fixtures, not reusing committed ones**, since dedup (both SHA-256 exact and pHash near-dup) would otherwise flag any 13 uploads of the same/similar-looking fixture as duplicates rather than populating a folder with 13 real cards. First attempt (same base JPEG + a few trailing padding bytes) still collided via pHash near-dup (identical pixel content) and resolved to `duplicate` instead of `done` — caught by an explicit `expect(status).toBe("done")` assertion rather than silently producing a smaller-than-intended folder. Fixed by generating 13 images from genuinely distinct random pixel noise via `sharp`, then using the same deterministic `sha256(bytes)[0] % 7` logic the mock classifier itself uses (read directly from `backend/src/lib/classification/index.ts`) to pre-select 13 byte-buffers that all happen to land in the Food category — avoiding any trial-and-error against the live server.
- **Signup rate-limit budget (5/15min/IP, live/unrelaxed since the dev server runs `NODE_ENV=development`) was tight but manageable across this run's 5 real signups** (main flow, cross-user isolation, pagination, double-click repro, and one bug-reproduction account) plus a few throwaway invalid-payload probes used only to check `RateLimit-Remaining` timing — following the prior report's own documented lesson, I checked response headers before assuming the bucket had reset rather than trial-and-erroring signups, and used an until-loop against the live 429 status rather than a blind fixed sleep. Total wall-clock cost from rate-limit waits: roughly 15 minutes across two windows.
- **`GET /api/dashboard`'s `totals.folderCount`** was independently cross-checked as a bonus assertion during the move test (item 8) — correctly reflects `2` after the move, consistent with the AI-classification and dashboard-stats cycles' prior behavior; no drift introduced by this build.
- **MinIO console login skipped on principle**, consistent with every prior report — thumbnail URLs were spot-checked as present/well-formed (pre-signed URL string or null) rather than a console visit.
- **Stale duplicate `tsx watch` processes are now present for BOTH `src/worker.ts` and `src/server.ts`** (previously only `src/server.ts` was flagged, in the last two reports) — confirmed via `ps aux`: a `Thu03AM`-started pair (`tsx watch src/worker.ts` / `tsx watch src/server.ts`, PIDs 86817/86224) alongside the live pair started `3:01AM` today (PIDs 66149/66148), plus one more solo stale `server.ts` watcher from `Wed08AM` (PID 15469). All benign (only one process per port can actually bind :4000, and BullMQ workers on the same Redis queue would double-process jobs if both were truly live and connected — worth a closer look next time someone's at the machine to confirm the stale ones aren't silently also consuming jobs, not just idling). Housekeeping, not a test failure.
