## Notes for Developer Agent

- **The G7 poll-claim handoff works exactly as the MR draft describes and is secure.** Verified live: approve returns no raw token to the owner; the guest's first status-poll observing `approved` mints the session, sets the httpOnly cookie on the polling browser, and only the SHA-256 hash lands in `guest_sessions`. The `session_claimed_at` latch is present. Behavior matches the spec's intent; the deviation from the literal "mint-at-approval" reading is sound (a raw token can't be recovered from a hash) and correctly localized.

- **Two harness artifacts encountered (NOT app bugs), documented so the next Tester doesn't misattribute them:**
  1. *Live auth rate limiters are armed* (server runs `NODE_ENV=development`, not `test`). Repeated HTTP signups/invite-requests during setup exhaust the signup (5/15min) and invite-request (10/15min) IP buckets, which then cascade 429s into unrelated scenarios. Worked around by (a) seeding owner accounts + sessions directly via Prisma to bypass the signup limiter for fixture setup only — the entire guest flow was still exercised black-box over HTTP — and (b) budgeting invite requests under 10 and waiting out the 15-min window for the starved scenarios. The rate limiter blocking past its bucket is itself a PASS.
  2. *A login-appears-to-fail red herring:* seeded owner accounts were inserted with a mixed-case email (`gtest-ownerA-...`), but `loginSchema` correctly `.toLowerCase()`s the input, so login looked up `gtest-ownera-...` and 401'd. This actually **validates** the app's email normalization — a real signup-created user stores a lowercased email and logs in fine (re-confirmed: after lowercasing the seeded row, login → 200 + session). No app defect; a fixture-generation mistake on my side.

- **Testability was excellent:** the flag-gated `GET /api/invites/requests/:requestId/otp` endpoint let me complete the live OTP flow without DB access exactly as the spec's Success Signal intends, and the observability on `otp_attempts`/`status`/`revoked_at` made every security transition DB-verifiable.

- **Housekeeping:** process tree clean — one `server.ts`, one `worker.ts`, one `next dev`, single `:4000` listener. No stale duplicates (the previously-flagged orphan remains gone). Test fixture data (7 users + cascaded guests/sessions/photos/permissions) cleaned up after the run.
