## Architecture additions

### Three frontend bug fixes (small, unrelated to each other, found via direct manual testing)

1. **Nav was inconsistent everywhere — `/upload` and `/organize` were unreachable by clicking anything.** Every authed page now carries the same full top-bar link set (Upload · Organize · Browse · Search · Guests · Activity, plus Trash added later this stretch). `/upload` and `/browse` previously had **no top bar at all**. If you add a new authed page, give it this same nav — there is no shared nav component yet (each page repeats the same `<Link>` block with the same CSS classes), so copy an existing page's top-bar markup rather than inventing a new pattern.
2. **`/upload` only accepted one file.** The backend's `upload.single("file")` contract (Day1) is unchanged and correct — the fix is entirely client-side: `frontend/src/app/upload/page.tsx` now tracks a list of per-file `UploadItem`s and loops the existing single-file endpoint with a **capped-parallel queue (3 concurrent workers)**, each item polling its own status independently. If you need true multi-file upload at the API level later (e.g. a single multipart-many-files request), that's still a real backend gap — this fix works around it client-side, it doesn't close it.
3. **A photo stuck `failed` or flagged `duplicate` had no manual way out.** The `PhotoCard` action area used to show exactly ONE control based on status (Reclassify OR "Not a duplicate?" OR a Move dropdown — never more than one). Now failed/duplicate cards show their retry action AND the Move dropdown together, so a photo that keeps failing (or a duplicate call you disagree with) can always be manually filed. This also exposed and fixed a second bug: moving a photo out of Unfiled wasn't decrementing the sidebar's Unfiled count.

### The Trash system — the major addition this stretch (spec: `specs/trash-system.md`, supersedes `specs/photo-deletion.md`)

**The premise changed mid-scoping.** The original ask was just "add photo deletion" (confirmed via code search: there was no delete-photo path anywhere, single or bulk). Abhishek then made an explicit, final product decision that deletion of **both photos and folders** must be a **reversible 7-day Trash**, not immediate/permanent — which meant *revising* the already-shipped, already-pushed Day5 folder-delete behavior (`057605c`/`9664b6b`), not just adding a new endpoint.

**Schema — one additive column, one genuinely new kind of constraint:**
- `deletedAt DateTime?` on both `Photo` and `Folder` (migration `20260707201747_add_trash_system`).
- **The tricky part:** `Folder`'s plain `@@unique([collectionId, name])` had to go, because a trashed folder would otherwise permanently occupy its name slot and block creating a new live folder with the same name. The fix is a **Postgres partial unique index** — `CREATE UNIQUE INDEX folder_active_name_unique ON folders (collection_id, name) WHERE deleted_at IS NULL` — hand-written into the migration's raw SQL, because **Prisma's schema DSL cannot express a partial index**. `schema.prisma` now has a plain non-unique `@@index([collectionId, name])` for query performance only; the REAL uniqueness constraint lives exclusively in that raw SQL. **This is loudly commented in both the migration file and schema.prisma for a reason: if anyone ever "fixes" the schema back to a plain `@@unique`, or drops the partial index thinking it's redundant, the trash-collision fix silently breaks.** Verified live: a trashed "Nature" + a new live "Nature" coexist fine; two *live* "Nature" folders still correctly 409-collide.

**Who's authoritative for deletion logic — `guestShareGuard.ts`, `purge.ts`, `trashPurgeJob.ts` (all new):**
- `guestShareGuard.ts` — the reusable `hasLivePermission()` check, promoted from the folder-only F1 guard (Day5/P4) to also gate single-photo deletes.
- **Decision, reversed from the Planner's first recommendation:** a single photo **cannot** be deleted if its folder has a live guest share — same 409 posture as the folder-level guard, no special case for "it's just one photo." (The original recommendation was to allow it since a single photo is lower blast-radius; Abhishek explicitly reversed this to match F1's stricter posture for consistency.)
- `purge.ts` — the shared hard-delete logic (DB row + MinIO cleanup + duplicate-chain cascade-null) used by BOTH the on-demand "delete forever" endpoint and the scheduled purge job, so there is exactly one place that does an irreversible delete.
- `trashPurgeJob.ts` — **new kind of infrastructure for this codebase**: a BullMQ *repeatable* job (`upsertJobScheduler`, registered idempotently at worker boot) running once daily, versus every prior job here being triggered per-event (upload → pipeline, reclassify → reclassify job). It purges anything with `deletedAt` older than 7 days. **Folder purge cascades to hard-delete its photos too**, even ones never individually trashed (they were only ever hidden *transitively* because their folder was hidden — see below) — this was an explicit decision (the alternative, spilling a purging folder's photos to Unfiled instead of destroying them, is logged as a real future feature request, not built). Idempotency is load-bearing: the job tolerates "already gone" on every step (a Prisma `P2025`, or a missing MinIO key) as a no-op success, and running it twice in a row must never double-decrement a counter or error.

**Photos in a trashed folder are hidden *transitively*, not individually marked.** When you trash a folder, its photos keep their `folderId` pointing at the (now-hidden) folder — they don't get their own `deletedAt`. Every query that resolves a folder's photos already checks the folder's visibility, so hiding the folder hides its contents for free, with zero per-photo bookkeeping. Restoring the folder brings everything back at once. **The corollary that bit this hardest during the build:** a photo is hidden if EITHER its own `deletedAt` OR its folder's `deletedAt` is set — every single listing path in the whole app had to check *both*.

**The 21-path listing-query audit — this is the part worth reading before touching any photo/folder listing code.** The spec enumerated every place in the app that lists photos or folders and had to be updated to exclude trashed items on both axes above: `/api/photos/unfiled`, `/api/photos/:id`, `/api/photos/:id/status`, `/api/folders/:id/photos`, folder rename/merge/delete, `PATCH /api/photos/:id` (move), reclassify, `/api/collections/:id/folders`, `/api/collections/:id/unfiled-photos`, `/api/search` (including its owner-scoped folder/category sub-lookups), all five guest-facing routes, and `/api/dashboard`'s stat rollups. **The single clearest "existing shipped code silently becomes wrong the moment trash exists" case:** `GET /api/folders/:id/download-all` (Day5's P5 bulk-zip feature) — a soft-deleted photo still has `status: done` and a real `s3Key`, so nothing about soft-delete on its own would have stopped it from being zippable. **If you ever add a new endpoint that lists or resolves photos/folders, it must filter on both `deletedAt` axes, full stop — this is the highest-leak-risk category of bug in this codebase now.**

**Restore isn't just "un-delete" — two composite behaviors worth knowing:**
- **Folder-restore name collision** (only reachable now, thanks to the partial-index fix, if you deliberately create a new folder with a trashed one's old name): `POST /api/folders/:id/restore` takes `{ onConflict?: "merge" | "rename", newName? }`. No conflict → restores normally. Conflict + no `onConflict` → `409 { error: "conflict", conflictingFolderId, conflictingFolderName }`. `"merge"` folds the restored folder's photos into the existing live one (reusing the P4 merge machinery) and discards the now-empty restored folder. `"rename"` + `newName` restores under a different name.
- **Restoring a photo whose folder is *also* still trashed** auto-restores the folder first (recursing into the same collision handling above) before restoring the photo — you never end up with a "restored" photo that's invisible because its container is still hidden.

**Audit** — 5 new additive action strings alongside the existing `photo_deleted`/`folder_deleted` (now semantically "moved to trash," not destroyed): `photo_restored`, `folder_restored`, `photo_permanently_deleted`, `folder_permanently_deleted`, `trash_emptied` (the last one is a single summary row per empty-trash action, not one row per item purged — a deliberate departure from the usual one-row-per-resource-event convention, since "empty trash" is conceptually one user action with a bulk effect).

**Endpoints:** `DELETE /api/photos/:id` + `POST /api/photos/bulk-delete` (soft-delete, partial-success shape for bulk — `{ deleted: string[], failed: [{id, reason:"not_found"}] }`), `DELETE /api/folders/:id` (revised — same F1 guard, now soft-deletes instead of hard-deleting + orphaning to Unfiled; **its response shape changed, `photosOrphaned` is gone**), `POST /api/photos/:id/restore` + `POST /api/folders/:id/restore`, and a new `routes/trash.ts`: `GET /api/trash` (both photos and folders, each with `deletedAt`/days-remaining), `DELETE /api/trash/:type/:id` (permanent, skip the wait), `DELETE /api/trash` (empty everything).

### The frontend: `/trash` page + real desktop-style multi-select on `/organize`

- **`/trash`** (new page, own top-bar entry): Photos/Folders tabs, a days-remaining badge that goes urgent-red under ~2 days, Recover, and a genuinely-irreversible Delete-forever with its own real confirm (an in-app dialog, not `window.confirm` — this project's standing rule for anything truly destructive). Empty-trash gets its own stronger confirm. The restore-collision 409 is resolved inline via a shared `CollisionPanel` component (merge-or-rename), reused for both the direct folder-restore path and the photo-restore-cascades-into-folder-restore path.
- **Multi-select on `/organize`** — genuinely mimics a desktop file manager, not just faster checkbox-clicking: hover reveals a checkbox; plain click toggles one card (replacing the selection); **Shift+click selects the contiguous range** from the last-clicked card; **Ctrl/Cmd+click toggles one card without touching the rest**; **click-and-drag from empty grid space draws a marquee** that replaces the selection on a plain drag but **extends** it if Shift/Ctrl was held at drag-start (the actual Finder/Explorer convention, not just a simplified "always replace"). "Select all on page" plus a genuine "select all N across all pages" that fetches every page's ids rather than just claiming to. The bottom action bar's delete confirm uses **reversible** copy ("moved to Trash, recoverable for 7 days") — the deliberate opposite tone from the Trash page's own permanent-delete confirms.
- **The T2 partial-result problem:** the backend's bulk-delete returns a uniform `reason: "not_found"` for every kind of per-item failure (not-owned, already-gone, or blocked by a live guest share) — it doesn't distinguish which. The UI can't fabricate a more specific reason than the backend gives it, so the message is honestly generic: "N deleted, M could not be deleted (already gone or currently shared with a guest)." If you want per-reason messaging later, the backend needs to return a real reason code, not just a UI change.
- **A stale confirm from Day5 got fixed in the same pass:** `/organize`'s single-folder delete confirm used to read a `photosOrphaned` field that no longer exists (nothing is orphaned anymore under soft-delete) — it now correctly says the folder and its photos move to Trash together, recoverable for 7 days.

## Testing (additions to Day1–5)

New `trash-system.smoke.test.ts` (35 tests). Backend suite: **137 → 173.** A comprehensive backend-only adversarial pass (the reversed guest-share guard, the partial-unique-index behavior, both restore-collision resolutions, permanent-delete, purge-job idempotency across repeated runs, and a spot-check of the highest-risk listing paths) came back clean. The UI pass verified the frontend's parsed response shapes match the live backend's actual output byte-for-byte, and — since simulating Shift-click/Ctrl-click/drag in a headless browser is unreliable in this environment — did a careful line-by-line **code review** of the selection logic instead of trying to automate the gestures, and found it correct (real DOM-rect intersection testing, the modifier captured at drag-*start* not drag-end, genuine multi-page fetching for "select all N").

**Known verification gap, carried forward from Day5:** there is still no Playwright/browser-automation tooling installed in this environment (confirmed absent this stretch, not just flaky) — nobody has watched pixels move on a screen for either the Trash page or the multi-select interactions. Everything reachable via HTTP + code inspection has been checked as hard as this project checks anything; the pure visual/click layer has not.

**A separate, real intermittent flake was investigated and characterized (not fixed) this stretch:** running the full backend suite repeatedly under heavy parallel load occasionally 404s a guest on a folder they legitimately have access to (`GET /api/guest/folders/:id/photos`), roughly 1 run in 4 in one investigation session, 0 in 9 in a later one. It never reproduces in isolation or light pairing — only under the full suite's DB connection load. **The failure direction is safe** (hides something, never leaks something it shouldn't) and it did NOT reproduce reliably enough to pin down a root cause in the trash-system code itself; the most credible lead is the test database's connection pool not being sized for how large the suite has grown (no `connection_limit` set in the test `DATABASE_URL`, Prisma's default pool × up to 13 parallel vitest processes vs. Postgres's `max_connections`). A separate, unrelated, pre-existing timeout flake (a rate-limit test hitting vitest's default 5s timeout under load) was also found in the same investigation. **If you see this specific guest-404 flake again, look at connection-pool sizing and `testTimeout` before assuming it's a logic bug in guest access.**
